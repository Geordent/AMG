1. Вывод: реестр должен быть отдельным исследовательским слоем
Для AMG я рекомендую JSONL-реестр кандидатов, хранящийся в Git отдельно от публикуемых данных. Он должен собирать не только подтверждённые достопримечательности, но и потенциально интересные объекты, найденные в муниципальных каталогах, научных публикациях, описаниях малых поселений, локальных маршрутах и профильных реестрах.

Главный принцип: кандидат — ещё не объект опубликованной карты. Найденное упоминание может оказаться дубликатом, частью более крупного комплекса, местом без безопасного доступа или объектом, для которого пока недостаточно фактов.

Предлагаемая модель совместима с известной структурой AMG без перестройки приложения:
- data/sites.geojson — канонические физические места с устойчивыми ID site-NNNN.
- data/experiences.geojson — отдельный слой активностей и туристических впечатлений; сейчас у его записей нет стабильных ID.
- data/artworks.json — произведения, связанные с местами через site_id.
- data/routes.json — остановки, ссылающиеся на ID мест.
- data/cities.json — названия населённых пунктов, но не полноценный справочник регионов и муниципалитетов.
По сохранённому аудиту Research 01 в sites.geojson было 573 места, в experiences.geojson — 60 объектов, а в routes.json — 4 маршрута. Это ориентир из аудита, а не заявление о повторно проверенном состоянии репозитория на сегодня.

Почему нельзя сразу объединять всё в sites.geojson
Одна туристическая остановка может быть:
- отдельным физическим объектом — пещерой, водопадом, монастырём;
- большим комплексом, включающим несколько зданий или памятников;
- населённым пунктом, где интерес представляет весь исторический ансамбль;
- коммерческой услугой — винодельней, канатной дорогой, конной прогулкой;
- маршрутом или событием, которые вообще не являются точечным объектом.
Если все эти сущности автоматически превращать в точки карты, возникнут дубликаты и неверные связи. Поэтому исследовательский реестр должен поддерживать разные типы сущностей и связи между ними, а решение о публикации должно приниматься отдельно.
2. Каталог источников и их практическая ценность
Ни один источник не следует считать исчерпывающим. Для максимального охвата нужно объединять официальные реестры, пространственные данные, тематические каталоги и региональные источники, проверяя найденные факты по возможности на независимых страницах.

1. Georgian National Tourism Administration — Georgia Travel

georgia.travel · условия использования

Назначение: туристические места, регионы, активности, культурные и природные объекты, готовые идеи поездок.

3. Финальная схема: JSONL с происхождением каждого утверждения
Почему JSONL, а не единый JSON
Одна строка — одна исследовательская запись. Это позволяет добавлять кандидатов из отдельных тематических исследований, объединять результаты нескольких поисковых проходов, сравнивать версии через Git diff и проверять записи простыми скриптами без отдельной базы данных.

Предлагаемое расположение:
research/
  registry/
    candidates.jsonl
    schema.md
    source-catalog.json
    decisions.jsonl


Это рекомендация по организации будущего исследовательского слоя, а не изменение файлов проекта.
3.1. Структура записи
Поле	Тип	Назначение
candidate_id	string	Стабильный внутренний ID, например AMG-C-000001. Никогда не переиспользуется
canonical_place_key	string/null	Внутренний ключ концептуального места, если несколько записей относятся к одному физическому объекту
names	object	Названия ka, en, ru, aliases с вариантами написания и транслитерации
entity_type	enum	Тип сущности: site, complex, settlement, experience, route, event, collection, other
categories	array	Тематические категории: heritage, nature, archaeology, wine, gastronomy, industrial, craft, museum, landscape и другие
tags	array	Поисковые признаки: cave, fortress, qvevri, abandoned, family, hiking и т. п.
geography	object	Регион, муниципалитет, населённый пункт и их названия на ka/en/ru; неизвестные значения — null
location	object	Координаты, геометрия при наличии, точность, метод определения, источник и дата проверки
description	object	Краткое оригинальное описание на ka/en/ru; язык без надёжного перевода можно оставить null
visitor_info	object	Сезонность, доступность, режим посещения, ограничения, часы и цены только при подтверждении
route_fit	object	Пригодность как остановки, ориентировочная длительность при наличии оснований, совместимость с другими точками
amg_links	object	Возможные связи с sites, experiences, artworks, routes; для каждого — статус сопоставления
identity	object	Внешние идентификаторы, варианты названия, признаки физического объекта, связи «часть комплекса»
verification	object	Статус поиска и проверки фактов, пробелы, конфликты между источниками
decision	object	Редакционное решение: рассмотреть, отложить или отклонить; причина и дата
claims	array	Утверждения, каждое со своим происхождением и ссылками на источники
audit	object	Дата создания, последняя проверка, исследовательский пакет, история изменений

Ключевое требование: источники привязываются к отдельным утверждениям. Например, официальный портал подтверждает статус памятника, муниципальная страница — принадлежность к поселению, а страница администрации парка — доступность тропы. Одна ссылка не должна автоматически подтверждать всё содержание карточки.
3.2. Статусы: три независимые оси
Не нужно смешивать факт нахождения объекта, степень проверки и редакционное решение.
Ось	Допустимые значения
Сопоставление с AMG	NEW_CANDIDATE, MATCH, POSSIBLE_DUPLICATE
Исследовательский статус	FOUND, UNDER_REVIEW, VERIFIED, INSUFFICIENT_DATA
Редакционное решение	CONSIDER, DEFER, REJECT

Значение VERIFIED означает, что существенные для карточки утверждения проверены подходящими источниками. Оно не означает, что объект уже опубликован или что каждый аспект его доступности известен.

Дополнительно каждое утверждение имеет эпистемический статус:
- confirmed — подтверждается указанным источником;
- inferred — вывод по совокупности данных, который нельзя выдавать за прямой факт;
- hypothesis — рабочая гипотеза, нуждающаяся в проверке;
- unknown — данных нет.

5. Идентификация и дедупликация с текущим AMG
Это наиболее критичная часть схемы. Нормализация названий и расстояние между координатами полезны, но сами по себе не доказывают, что две записи описывают одно место.
5.1. Безопасный алгоритм сопоставления

Шаг 1. Поиск точного соответствия

Сравнить официальные идентификаторы, ссылки на первоисточники, названия на грузинском и существующие внешние ID. Если совпадает физический объект, связать кандидата с канонической записью AMG.




Шаг 2. Пространственное сравнение

Сравнить расстояние между точками, тип геометрии и названия. Использовать несколько радиусов поиска, например 25, 100 и 250 метров, как сигналы для проверки, а не автоматические правила слияния.

Для больших комплексов, водопадов, пещер и поселений расстояние до центра может быть менее полезно, чем совпадение границ или принадлежность к одному комплексу.




Шаг 3. Проверка семантики

Установить, описывают ли записи одно физическое место, разные части одного комплекса, отдельные услуги в одном здании или разные объекты с похожими названиями. Не объединять две достопримечательности только потому, что они расположены рядом.




Шаг 4. Фиксация решения

Записать результат сопоставления, обоснование, найденные ID и дату проверки. Не изменять существующую запись AMG до принятия решения о публикации.



5.2. Что считать совпадением
Ситуация	Решение
Одно место, несколько вариантов названия	MATCH; сохранить все варианты как aliases
Одно место, но кандидат содержит более качественные источники	MATCH; сохранить ссылки на существующую сущность и отметить новые сведения
Кандидат — отдельное здание внутри уже известного комплекса	Проверить, нужна ли самостоятельная остановка; не сливать автоматически

Существующая точка расположена неверно	Не считать совпадение доказанным только по названию; отдельно фиксировать конфликт координат
Нет результатов поиска в AMG	Только после полного сопоставления можно поставить NEW_CANDIDATE

5.3. Особый случай experiences.geojson
По Research 01, в текущем слое 60 объектов без стабильных ID. Поэтому опасно присваивать им ID на основании номера строки или позиции в файле: порядок может измениться, а один объект — исчезнуть или быть заменён.

Безопасный механизм:
1. Для каждой текущей записи создать исследовательский отпечаток из нормализованных названий на всех доступных языках, kind, адресов, координат и сайта, если он есть.
2. Сохранить этот отпечаток в отдельном файле соответствий, например experience-identities.jsonl.
3. При каждом обновлении искать соответствие по нескольким признакам, а не только по хешу полного содержимого.
4. Если запись изменилась, но физический объект остался тем же, сохранить прежний внутренний ID и обновить отпечаток.
5. Если возможны несколько совпадений, не выбирать автоматически — пометить их как неоднозначные.
6. Если объект удалён из исходного слоя, не удалять его историю из реестра; сохранить статус сопоставления и дату последнего обнаружения.
Пример записи соответствия:
{
  "identity_id": "AMG-EXP-ID-000001",
  "legacy_layer": "data/experiences.geojson",
  "legacy_fingerprint": "sha256:...",
  "identity_basis": {
    "name": true,
    "kind": true,
    "location": true,
    "website": false
  },
  "match_status": "UNASSESSED",
  "last_seen_at": "2026-10-29"

sha256:... здесь — схема поля, а не реально рассчитанный хеш. До вычисления отпечатка и проверки текущих записей его нельзя использовать как идентификатор реального объекта.
6. Происхождение данных и обновление
6.1. Каждое утверждение должно быть проверяемым
Пример корректной модели происхождения:
Утверждение	Предпочтительный источник	Что он не подтверждает автоматически
Объект имеет статус культурного наследия	Официальный портал наследия	Что он открыт для туристов
Объект находится в охраняемой территории	APA или соответствующий пространственный набор	Что посещение разрешено в любое время
Точка находится в конкретном муниципалитете	NSDI и официальные административные границы	Что муниципалитет поддерживает туристическую инфраструктуру
Винодельня принимает посетителей	Действующая страница самой винодельни или подтверждение организатора	Что дегустация доступна без бронирования
Фестиваль пройдёт в определённый день	Официальный анонс конкретного выпуска	Что событие будет ежегодно проходить в ту же дату
Исторический объект датируется определённым веком	Профильная научная публикация или официальный каталог	Что все популярные легенды об объекте исторически достоверны

Если два источника противоречат друг другу, сохранять оба утверждения, даты и происхождение. Не перезаписывать историю так, будто предыдущих сведений не существовало.
6.2. Даты и повторная проверка
Рекомендуется различать три даты:
- published_at — дата публикации первоисточника, если известна;
- checked_at — дата, когда исследователь проверил утверждение;
- valid_from / valid_to — период, к которому относится сам факт, если это важно.
Для часов работы, цен, бронирования, временных закрытий и событий проверка должна быть чаще, чем для геологии или исторической датировки. Не нужно считать старую страницу доказательством актуальной доступности.
6.3. Правила обновления реестра
- Добавление: новый кандидат получает новый candidate_id; прежние ID никогда не переиспользуются.
- Исправление: сохраняется история значимых изменений, особенно статусов, координат и источников.
- Слияние: обе записи сохраняются; одна становится основной, вторая указывает same_place_as и причину слияния.
- Разделение: если выяснилось, что один кандидат описывал несколько объектов, создаются отдельные записи с перекрёстными ссылками.
- Отклонение: запись не удаляется. Фиксируется причина — например, несуществующий объект, нерелевантность, дубликат или недостаточность доказательств.
- Изменение статуса: не должно автоматически публиковать или удалять данные AMG.
- Лицензии: хранить отдельно от фактических утверждений. Возможность прочитать информацию не означает право копировать описание или фотографию.
- Описание: составлять собственными словами, избегая близкого перефразирования защищённого текста. Сохранять факты и ссылку на источник, а не чужую редакционную формулировку.
7. Рекомендации по дальнейшим тематическим исследованиям
Уже проведённые исследования культурного наследия, природы и винной культуры дают стартовый набор, но не гарантируют полного регионального покрытия. Следующий цикл должен расширять охват и одновременно использовать реестр как общий механизм сбора.

1. Муниципальные каталоги и малые поселения

Наивысший приоритет для расширения географии

Систематически пройти муниципалитеты Грузии, в первую очередь страницы на грузинском языке. Собирать локальные достопримечательности, небольшие церкви, исторические кварталы, традиционные дома, мемориалы, мосты, смотровые точки и местные праздники. Вести таблицу «муниципалитет → источники проверены → страницы просмотрены → кандидаты найдены → пробелы».




2. Природа вне известных охраняемых территорий

Дополнить официальный перечень APA геологическими образованиями, водопадами, озёрами, ледниками, перевалами, ущельями и ландшафтными объектами. Использовать NSDI для пространственной проверки и научные публикации для подтверждения происхождения и характеристик.




3. Индустриальное, советское и инженерное наследие

Чиатура, Цхалтубо, Рустави, Зестафони и другие промышленные районы: шахты, старые станции, канатные дороги, фабрики, гидротехнические сооружения, мозаики, модернистские здания и заброшенные объекты. В обязательном порядке фиксировать право доступа, опасность и различие между сохранившимся памятником и действующим аттракционом.




4. Вино, гастрономия и ремёсла

Помимо виноделен: традиционные пекарни, сыроварни, рынки, мастерские, ткачество, ковроткачество, гончарные центры, локальные пищевые традиции. Различать постоянно доступные места и услуги по предварительной договорённости.




5. Маршруты и малые тропы

Проверять не только официальные тропы национальных парков, но и региональные пешие маршруты, исторические дороги, сельские круговые маршруты и маршруты к отдельным объектам. Хранить сам маршрут как отдельную сущность и связывать его с остановками по устойчивым ID.




6. События и нематериальное наследие

Региональные праздники, сезонные ритуалы, ремесленные ярмарки, музыкальные традиции, локальные фестивали и обряды. Сохранять сведения о культурной практике отдельно от дат конкретных мероприятий.



Итог
Реестр кандидатов должен стать проверяемым каталогом исследовательских находок, а не второй опубликованной картой. Он позволит постепенно наращивать охват AMG, сохраняя происхождение каждого факта, неизвестные поля, неоднозначные совпадения и редакционные решения.

Критические требования к реализации:
1. JSONL и Git, без отдельной базы данных.
2. Устойчивые внутренние ID и явная связь с каноническими сущностями AMG.
3. Источники, привязанные к конкретным утверждениям.
4. Раздельные статусы сопоставления, проверки и редакционного решения.
5. Особый механизм идентификации для experiences.geojson.
6. Отсутствие автоматической публикации.
7. Систематический региональный сбор, прежде всего по муниципальным и грузиноязычным источникам.
Ничего в опубликованных данных или коде проекта в ходе этого исследования не изменялось.
